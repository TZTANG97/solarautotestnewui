# 增量迁移约定：改到哪里就迁移到哪里

> 适用仓库：`solarautotestnewui`  
> 生效日期：2026-09-02  
> 配套：`.cursor/rules/incremental-migration.mdc`（Agent 始终遵循）  
> 背景：根目录与 `SCPITestWave.py` 过载；不做一次性大搬家，用修 BUG 的机会渐进整理。

---

## 1. 一句话原则

**修什么，就只把「本次真正改到的那一块」迁到约定目录；没改到的别动。**

先修对行为，再做同范围迁移。迁移是修 BUG 的附带整理，不是独立重构任务。

---

## 2. 什么叫「改到了」

算触及、应顺手迁移：

- 修改了某试验的 `xxxSend` / `xxxAppend` 逻辑
- 在 `SCPITestWave.py` 里为某试验新增超过约 30 行业务代码
- 复制粘贴后需要第二处共用的纯函数 / UI 片段
- 根目录又要加一次性脚本、补丁、冒烟文件

不算触及、不要顺手迁：

- 只改配置文案、默认值、注释
- 只改日志或异常提示字符串
- 只读参考已绿试验（闪变等）的代码
- 「看起来乱」但本次 diff 未修改的相邻函数

---

## 3. 目标落点

| 代码类型 | 迁往 | 说明 |
|---|---|---|
| `xxxSend` / `xxxAppend` | `sends/<project>_send.py` | 主文件保留同名函数转调，避免一次改光所有接线 |
| 试验命令/录波纯函数 | `utils/<topic>.py` | 已有 `utils/ovuf_recording.py`、`utils/wt_recording_mode.py` 等范式 |
| 共用 WT/录波 UI | `components/` | 如 `wt_recording_mode_row.py` |
| 设备连接与发令 | `devices/` | 创建/断开/重连一起迁，避免第三份真源 |
| Dialog UI | 暂留 `Dialog_*.py` | 整文件大改时再迁 `dialogs/`，并保留兼容导入 |
| 正式回归测试 | `tests/` | pytest 可跑 |
| 一次性脚本/补丁 | `code_example/` 或 `scripts/scratch/` | 禁止继续堆根目录 |
| 运行产物 | `data_logs/`、`command_save_files/`、`dist/` | 不入库（gitignore） |

新建目录时：若 `sends/` 尚不存在，**第一次**抽出某个 Send 时再创建，不要空建一堆文件夹。

---

## 4. 标准作业流程（修 BUG 时）

1. **定位最小改动面**：先复现，确认要改的函数/文件。
2. **修行为**：在原处或已有模块里把 BUG 修对。
3. **同范围迁移**（仅当本步骤改动面满足第 2 节）：
   - 抽出纯函数 → `utils/`
   - 抽出该试验 Send/Append → `sends/`
   - `SCPITestWave.py` 改为 `from sends.xxx import xxxSend` 或薄包装
4. **删旧路径**：不要保留两份可执行逻辑。
5. **验证**：至少保证启动 + 该试验生成命令/相关单测通过。
6. **停手**：未触及的试验、执行器大拆、Dialog 包重命名 —— 都不做。

---

## 5. 与「已绿试验」的关系

进度上已绿、且用户未点名返工的项目（闪变、谐波、固定 PF、过载、直流分量、重连、过欠压_过欠频等）：

- **默认不要**为整理而打开迁移
- 若后续真有 BUG 必须改其 Send：允许按本约定只迁该试验相关代码
- 共用层（如 `components/wt_config_content.py`）变更要评估对已绿项的影响，优先向后兼容

---

## 6. 禁止清单

- 一次任务里同时：搬目录 + 改设备协议 + 换执行线程模型
- 为通过「看起来整齐」而全仓改 import
- 长期双写：`SCPITestWave.py` 与 `sends/` 各维护一套 Send
- 把 `dist/`、日志、命令 CSV、`__pycache__` 当源码一起整理进业务目录

---

## 7. 完成检查（每次迁移）

- [ ] 行为与 BUG 修复目标一致
- [ ] 新模块有明确职责，命名与试验/主题对应
- [ ] 旧调用点已改为导入新位置
- [ ] 无双写逻辑
- [ ] `uv run python SCPITestWave.py` 可启动（或说明仅库级改动）
- [ ] 相关 `tests/` 或最小冒烟已跑

---

## 8. 和架构长文的关系

`项目架构维护指南.md` 描述目标分层与阶段 A–E。  
**本约定是日常执行方式**：不靠专项重构周，而靠每次修 BUG 推进一步阶段 D（抽取项目实现）和目录卫生。

大改执行器 / AppContext 所有权仍按维护指南阶段 A–C 单独立项，不塞进普通 BUG 单。
